# Plan: Fix H1 — SEV-SNP quote-signature / cert-chain exemption on `tinfoil_v3_cloud`

## Context

The 2026-07-02 security review found a High-severity fail-open (H1). For
`tinfoil_v3_cloud`, the default policy (`TinfoilCloudDefaultAllowFail`,
`internal/attestation/report.go:408-420`) exempts the two factors that
cryptographically authenticate the hardware quote — `FactorTEECertChain`
("tee_cert_chain") and `FactorTEEQuoteSignature` ("tee_quote_signature"). Every
measurement and key-binding factor derives its values from that same quote, so
exempting the signature removes the only thing that makes them trustworthy: a
forged quote passes, `Blocked()` returns false, and E2EE proceeds to an attacker
key. Hardware attestation collapses to TLS trust.

**Empirically confirmed corrections to the review's framing:**
- `tinfoil_v3_cloud` is **SEV-SNP** (AMD Genoa), not TDX. Captured fixtures fetch
  `kdsintf.amd.com/vcek/v1/genoa/...` and the attestation body says
  `"platform":"sev-snp"`. Only `tinfoil_v3_direct` is TDX (Intel PCS). So the H1
  exposure is entirely on the **SEV code path**.
- Tinfoil does **not** staple the AMD cert chain. The attestation body's
  `certificate` field is only the TLS leaf cert (for TLS-key binding); the `cpu`
  object carries just `platform` + raw `report` bytes. The VCEK must be fetched
  from AMD KDS; the only availability lever is **caching** it.

**Root cause of the over-broad exemption.** In `internal/attestation/sev.go`,
`VerifySEVReportOnline` (~253-280) calls `sevverify.RawSnpReportContext`, which
fetches the VCEK from KDS *and* verifies chain + signature in one call. On **any**
error — including KDS being unreachable — it sets both `CertChainErr` and
`SignatureErr`, which the report builder renders as `Fail`. The code therefore
cannot distinguish "KDS is down" (availability) from "KDS rejected a forged quote"
(cryptographic forgery); both collapse to the same failure. The blanket exemption
exists to stop a KDS outage from blocking all cloud traffic — at the cost of the
security hole.

**Intended outcome.** Split fetch from verification so the two failure modes are
distinguishable, cache the long-lived VCEK so KDS outages stop mattering per
request, and make a definitive cryptographic failure non-exemptible. Per
AGENTS.md (lines 55, 61: strictness over service; 141-149: no fallbacks/
workarounds), a genuinely unobtainable VCEK in the live serving path **fails
closed**; `--offline` remains the one sanctioned skip for this network-dependent
check.

## Design overview

Three coordinated changes, plus a new cache file and tests:

1. **Split the fused verify** in `sev.go` into a KDS *fetch* phase and an offline
   *crypto-verify* phase, using the split `go-sev-guest` v0.15.0 API.
2. **Classify failures** into a new `FetchErr` (availability) vs the existing
   `SignatureErr`/`CertChainErr` (cryptographic) on `SEVVerifyResult`, and render
   them distinctly in `report.go` — crypto and (online) `FetchErr` both `Fail`
   with distinct, non-secret diagnostics.
3. **Make the factors genuinely enforced** by removing them from
   `TinfoilCloudDefaultAllowFail` and adding them to `OnlineFactors` (so
   `--offline` — the one sanctioned network skip — still waives them), and add a
   `BuildReport` override so a *cryptographic* failure is non-exemptible **even if
   an operator re-adds the factor to their own `allow_fail`**.

This yields the policy split AGENTS.md line 71 implies: a cryptographic forgery is
never waivable (the override always blocks it); a pure KDS-availability failure
fails closed by default but remains waivable through the sanctioned `allow_fail` /
`--offline` mechanisms, where the operator consciously accepts the availability-vs-
security tradeoff. This is the codebase's existing idiom — every other online
factor (e.g. `intel_pcs_collateral`) is "in `OnlineFactors`, absent from the
provider allow-list ⇒ enforced online, skipped under `--offline`."

Note (confirmed by the Plan pass): the integration fixtures already hard-assert
`tee_cert_chain`/`tee_quote_signature` must PASS for the cloud SEV fixture
(`verify_run_test.go:180-185`, `helpers_test.go:165-168`), so the genuine KDS
crypto path succeeds today and the split preserves it.

## go-sev-guest v0.15.0 API (confirmed from module source)

- `verify.GetAttestationFromReportContext(ctx, *spb.Report, *verify.Options) (*spb.Attestation, error)`
  — fetches ASK/ARK (`trust.GetProductChainContext`, which has a built-in product
  cache) and the per-chip VCEK (`kds.VCEKCertURL(...)` + `trust.GetWith`). Returns
  an `Attestation` with `CertificateChain{VcekCert, AskCert, ArkCert}`. **Every
  error here is a fetch/availability error** (VCEK failures wrapped in
  `trust.AttestationRecreationErr`). This is the fetch phase.
- `verify.SnpAttestationContext(ctx, *spb.Attestation, *verify.Options{DisableCertFetching:true})`
  — with cert-fetching disabled, does **no network**: validates chain-roots-to-AMD
  (embedded roots when `TrustedRoots==nil`) then report signature. This is the
  crypto phase.
- `verify.SnpProtoReportSignature(*spb.Report, *x509.Certificate) error` — pure
  offline signature check, used to attribute signature-vs-chain fault.
- `trust.ParseCert([]byte) (*x509.Certificate, error)` — parse the DER VCEK.
- There is **no built-in VCEK cache** in `trust` (only ASK/ARK). teep must cache
  the VCEK/chain itself.
- Test helpers (`go-sev-guest/testing`): `AmdSignerBuilder`, `DefaultVcek/Ask/Ark`,
  `FakeKDS`, `GetKDS(t)`, `TestReportOptions`, `CreateRawReport` — for genuinely
  signed reports + fake KDS with no real network.

## Changes

### 1. `internal/attestation/sev.go`

- **Extend `SEVVerifyResult`** (~83-124): add `FetchErr error` — VCEK/chain could
  not be retrieved *and* no cached chain was available (the availability signal,
  mutually exclusive with the crypto errors). Document the invariant: online path
  yields exactly one of `FetchErr != nil` (availability) / one-or-both crypto
  errs (forgery) / `OnlineVerified == true`.
- **Rewrite `VerifySEVReportOnline`** to take a `*SEVCertCache` and do fetch →
  cache-check → offline verify. Sketch (decompose into named helpers to stay under
  gocyclo 32, AGENTS.md line 112):
  1. `reportProto, _ := sevabi.ReportToProto(report)` (ParseErr already handled).
  2. `key := sevCacheKey(reportProto.GetChipId(), reportProto.GetReportedTcb())`.
  3. `chain, ok := cache.Get(key)` (nil-safe).
  4. If miss: `att, err := verify.GetAttestationFromReportContext(ctx, reportProto,
     &verify.Options{Getter: getter, Now: verifyNow})`. On `err` → set
     `result.FetchErr`, log a non-secret diagnostic at warn, return. Else
     `chain = att.GetCertificateChain()`.
  5. Crypto phase (no network): `att := &pb.Attestation{Report: reportProto,
     CertificateChain: chain}`; `combErr := verify.SnpAttestationContext(ctx, att,
     &verify.Options{DisableCertFetching: true, Now: verifyNow})`.
  6. `combErr == nil` → `result.OnlineVerified = true; cache.Put(key, clone(chain))`.
     Else attribute: parse VCEK (`trust.ParseCert(chain.GetVcekCert())`); if
     `SnpProtoReportSignature` fails → `result.SignatureErr`; else
     `result.CertChainErr = combErr`. Cache only on `OnlineVerified`.
- **`NewSEVVerifier`** (~288-295): construct one `SEVCertCache` per verifier and
  close over it (cache owned as a struct value — no package-level state).
- (Recommended) thread a `verifyNow time.Time` from `opts.VerificationTime`
  (verify.go:33-36) into `NewSEVVerifier(offline, getter, now)` and on into both
  phases' `verify.Options{Now: now}`, matching the existing PoC/NRAS pattern. This
  updates the two call sites (`internal/verify/verify.go:85`,
  `internal/proxy/proxy.go:478`) and keeps replay/aging-fixture semantics correct.
  If deferred, SEV cert validity falls back to `time.Now()` (latent replay risk).

### 2. New `internal/attestation/sevcert.go` — concurrency-safe VCEK cache

Mirror `internal/attestation/spki.go` (AGENTS.md lines 97-101: no package-level
mutable state; `sync.RWMutex`; concurrent tests):
- `type SEVCertCache struct { mu sync.RWMutex; ttl time.Duration; entries map[string]sevCertEntry }`,
  `sevCertEntry{ chain *pb.CertificateChain; addedAt time.Time }`.
- `NewSEVCertCache()` with `ttl = 24h` (VCEK is per-chip/per-TCB and long-lived;
  `reportedTcb` is in the key, so a TCB change is a distinct entry — no downgrade
  risk), size cap (e.g. 1024) with oldest-eviction like `SPKICache.Add`.
- `Get(key) (*pb.CertificateChain, bool)` — RLock, TTL check, return a
  `proto.Clone` so callers can't mutate the cached proto. `Put(key, chain)` —
  Lock, prune expired, evict if over cap, store a clone. All methods
  nil-receiver-safe. `sevCacheKey(chipID []byte, reportedTcb uint64) string` =
  `hex(chipID) + "|" + strconv.FormatUint(reportedTcb,16)`.
- Cache-miss triggers a real fetch, never a pass-through; eviction only forces
  re-fetch, never unattested acceptance (AGENTS.md lines 81-82). Because the crypto
  phase (Helper B) re-runs on every request, a cache hit only supplies certificate
  bytes, never a verdict.

### 3. `internal/attestation/report.go`

- **`evalSEVParseDependent`** (~908-957): replace the fused Fail/Pass/Skip blocks
  with `FetchErr`-aware rendering, crypto checked before availability. For
  `tee_quote_signature`: `SignatureErr` → **Fail** (signature invalid);
  `OnlineVerified` → **Pass**; `CertChainErr` → **Skip** (cross-fault; the chain
  factor carries the block); **`FetchErr` → Fail** ("AMD KDS unreachable and no
  cached VCEK; cannot verify — failing closed (use --offline to bypass
  network-dependent checks)"); default (offline, all-nil) → **Skip** (existing
  "offline mode … requires AMD KDS"). Symmetric for `tee_cert_chain`
  (`CertChainErr` → Fail; `SignatureErr` → Skip cross; `FetchErr` → Fail). The two
  distinct Fail messages (crypto vs. availability) satisfy "fail loudly, distinct
  diagnostic" (AGENTS.md line 70).
- **Enforcement override** at the `BuildReport` append loop (~714-719), after
  `f.Enforced = !allowFailSet[f.Name]`, gated on `f.Status == Fail` (the gate
  keeps an offline-mode `Skip` from ever being force-enforced-then-promoted):
  ```go
  if f.Status == Fail && isCryptoAuthFactor(f.Name) {
      // Cryptographic authentication of the hardware quote is never exemptible,
      // even if an operator re-added the factor to allow_fail. TDX cert/sig is
      // offline and free — always enforce. SEV: enforce a definitive crypto
      // verdict; a pure KDS-availability failure (FetchErr) is NOT covered here,
      // so it follows the allow_fail list and --offline can waive it.
      if in.TDX != nil || (in.SEV != nil && (in.SEV.SignatureErr != nil || in.SEV.CertChainErr != nil)) {
          f.Enforced = true
      }
  }
  ```
  with `isCryptoAuthFactor` matching `FactorTEECertChain`, `FactorTEEQuoteSignature`,
  `FactorGWCertChain`, `FactorGWQuoteSignature`. Note the override deliberately
  covers only the *crypto* errors, not `FetchErr` — availability blocks by default
  (factor removed from the list, below) but stays operator-waivable.
- **`TinfoilCloudDefaultAllowFail` (report.go:408-420): remove** `FactorTEECertChain`
  and `FactorTEEQuoteSignature`. Update the rationale comment (report.go:390-407)
  to the fail-closed model (VCEK fetched and cryptographically enforced; cache
  absorbs KDS flakiness after first contact; only a cold-cache outage blocks, only
  `--offline`/`allow_fail` waives it). No audit identifiers in the comment (line 49).
- **`OnlineFactors` (report.go:469-482): add** both factors, so `WithOfflineAllowFail`
  unions them under `--offline`. Safe for TDX (TDX crypto verifies offline against
  the embedded PCK chain, and the `in.TDX != nil` override re-enforces a genuine
  TDX crypto failure even in offline mode).
- `KnownFactors` unchanged (both names already present).

Why block/no-block lands correctly:
- SEV crypto forgery → `Fail` + override → `Enforced` → `Blocked()==true`, even if
  an operator re-listed the factor. **H1 closed permanently.**
- SEV VCEK unobtainable (online, cold cache) → `FetchErr` → `Fail`, enforced by
  default (removed from list) → `Blocked()==true`. **Fail closed** per AGENTS.md;
  operator can waive via `allow_fail`/`--offline` if they accept the tradeoff.
- SEV `--offline` → offline verifier sets no error fields → `Skip`; factor unioned
  into allow-fail via `OnlineFactors` → not enforced → **not blocked**. Sanctioned
  skip preserved.
- Warm cache during a KDS outage → offline verify succeeds → `Pass` → not blocked.
- TDX cert/sig failure → `Fail` + override (`in.TDX != nil`) → blocks (defense in
  depth for `tinfoil_v3_direct` and any operator who allow-lists these).

## Constraints (AGENTS.md)

- No package-level mutable state; cache on a struct, `RWMutex`-guarded, concurrent
  `-race` tests (97-101). Fail loudly with non-secret diagnostics (63, 70). No
  audit identifiers in code comments or commit messages (49); reference the finding
  only in this plan/PR discussion. Regression tests required for the finding (139).
  Constant-time compares for any fingerprint/hash (87). Decompose the split
  fetch/verify into named helpers up front — gocyclo ≤ 32 (112). One commit per
  phase (43); suggested phases: (1) cache + sev.go split + classification,
  (2) report.go rendering + override, (3) tests + integration assertion.

## Open questions / risks

- **Policy (main decision):** plan implements **fail-closed** on an unobtainable
  VCEK (removed from the default allow-list). Availability during a cold-cache KDS
  outage is recoverable only via the sanctioned `allow_fail`/`--offline` opt-ins.
  Fail-soft (render `FetchErr` → `Skip` and keep the factors in the list) is the
  documented alternative if outage-availability is later judged to outweigh the
  residual network-attacker hole — but that contradicts the AGENTS.md philosophy.
- **`OnlineFactors` addition affects TDX under `--offline`:** adding the two
  factors to `OnlineFactors` waives them for *all* providers under `--offline`,
  including TDX. TDX is protected by the `in.TDX != nil` override (TDX crypto is
  offline-verifiable and a genuine TDX crypto failure still blocks). If maintainers
  prefer not to rely on the override here, the alternative is a SEV-scoped offline
  exemption rather than a global `OnlineFactors` entry.
- **Both-bad attribution:** `SnpAttestationContext` returns one error (chain-first);
  we re-check signature via `SnpProtoReportSignature` to attribute. If both are bad,
  only the signature factor shows Fail (chain shows Skip); security is unaffected
  (at least one crypto factor blocks) — only the human-readable detail is imperfect.
- **Cache persistence:** in-process only; a cold start during a KDS outage
  fails closed until KDS recovers (acceptable under the fail-closed policy;
  disk-persist is a possible later enhancement).
- **Revocation:** `CheckRevocations` stays false (unchanged); 24h TTL + TCB-in-key
  bound staleness. Note for any future CRL work.
- **Future:** if tinfoil ever staples the VCEK/chain in its attestation body, the
  fetch phase can pre-populate `att.CertificateChain` and skip KDS entirely — best
  availability, no cache needed. Not available today (confirmed).
