# Plan: GH issue #113 — Venice ACI/1 attestation format not parsed

Issue: https://github.com/13rac1/teep/issues/113

## Context

Venice now runs two TEE stacks. 10 of 13 models (as of 2026-06-26) return a
new `aci/1` format (`api_version: "aci/1"`, vendor `private-ai-gateway-dev`)
that teep does not parse. The attestation data exists but in different JSON
locations, so parsing yields empty `AppCompose`/`EventLog` and four
**enforced** factors fail: `compose_binding`, `sigstore_verification`,
`event_log_integrity`, `build_transparency_log`. (Venice uses the global
`DefaultAllowFail` — `internal/config/config.go:57-65` has no venice entry —
and none of the four are in it, so they Skip→Fail-promote and block. That is
correct fail-closed behavior; the fix is to parse the new format, not to
relax the factors.)

Current parsing (`internal/provider/venice/venice.go`):

- `attestationResponse` (:148-178) decoded strictly via
  `jsonstrict.UnmarshalWarn` (:227) in `ParseAttestationResponse`
  (:225-271).
- Compose comes only from `info.tcb_info.app_compose` (:260); event log
  only from top-level `event_log` (:261). `BackendFormat` is hardcoded
  `FormatDstack` (:243).
- No "ACI" string exists anywhere in the codebase — the format is entirely
  unsupported.
- `internal/formatdetect.Detect` (:29-46) sniffs top-level keys
  (`format`→Tinfoil, `attestation_type`→Chutes, `gateway_attestation`→
  Gateway, `intel_quote`→Dstack) and is used only by nanogpt and
  phalacloud. An ACI/1 body has top-level `intel_quote`, so today's
  detector would *misclassify* it as plain dstack.

## Design

Treat ACI/1 as a new backend format with its own parser and report-data
verifier, dispatched per response — mirroring how phalacloud already handles
multi-format via `multi.Verifier{Verifiers: map[BackendFormat]ReportDataVerifier}`
(`internal/verify/factory.go:93-98`).

### 1. New format constant + detection

- Add `FormatACI` to `attestation.BackendFormat`
  (`internal/attestation/attestation.go:74-81`).
- Extend `formatdetect.Detect`: probe `api_version`; value `"aci/1"` →
  `FormatACI`. Order the check before the `intel_quote` → dstack rule
  (ACI/1 bodies also carry top-level `intel_quote`). Any *other*
  `api_version` value → fail loudly (unknown version is a parse error, not
  a silent dstack fallback).
- Venice stops hardcoding `FormatDstack`: `ParseAttestationResponse` calls
  `formatdetect.Detect` (or checks `api_version` directly) and dispatches to
  the dstack parser or the new ACI parser. Unknown format → error (fail
  closed).

### 2. ACI/1 parser (`internal/provider/venice/aci.go`, new)

Strict structs for the documented shape, decoded with
`jsonstrict.UnmarshalWarn`:

- top level: `api_version`, `workload_id` (sha256 digest), `attestation`,
  `intel_quote`, `nvidia_payload`, `signing_public_key`, `signing_algo`,
  `signing_address` (+ whatever the live capture shows — build the struct
  from a real capture, not just the issue's example).
- `attestation`: `vendor`, `tee_type`, `workload_keyset`, `report_data`,
  `source_provenance` (`repo_url`, `repo_commit`, `image_digest`,
  `image_provenance`), `evidence` (`quote`, `event_log`, `vm_config`,
  `key_custody`, `downstream_tls_binding` {`domain`, `spki_sha256`}).

Mapping into `RawAttestation`:

- `EventLog` ← `attestation.evidence.event_log` (reuse
  `eventLogFlexible`-style decoding; the payload may be a JSON-encoded
  string). RTMR replay then reuses `attestation.ReplayEventLog`
  (`internal/attestation/eventlog.go:14-40`) unchanged →
  `event_log_integrity` works.
- Quote ← `intel_quote` (same as dstack) → TDX verification unchanged.
- `SigningKey` ← `signing_public_key`; nonce/report-data per the ACI
  `report_data` field — confirm the binding formula from live data (see
  Open questions) and implement a dedicated `ReportDataVerifier` for
  `FormatACI`, registered via `multi.Verifier` in
  `internal/verify/factory.go:84-106` for venice (dstack + ACI entries).
- `VMConfig` ← `attestation.evidence.vm_config`.

### 3. Supply chain: source provenance instead of compose

ACI/1 has no `app_compose`; it has `source_provenance{repo_url,
repo_commit}` and a `workload_id` digest. Options:

- **Recommended:** add an ACI supply-chain path that (a) verifies
  `compose_binding`'s ACI analog — bind `workload_id` (and/or
  `report_data`) into the quote's MRCONFIGID/RTMR per the vendor's scheme,
  and (b) drives `build_transparency_log`/`sigstore_verification` from
  `source_provenance` + `image_digest` when present. Where the ACI response
  provides *no* verifiable image digests (the example shows `image_digest:
  null`), the factors must **Fail (enforced)** for those models until
  Venice publishes verifiable provenance — do not mark them
  `NotApplicable`. Blocking here is the intended fail-closed outcome;
  surfacing it clearly in the report is the deliverable.
- Coordinate with issue #118: the new supply-chain policy shape should
  cover "git repo + commit" provenance (`SourceRepos` on
  `ImageProvenance` already points this direction) so ACI models get a
  reviewed policy rather than ad-hoc logic.

### 4. TLS binding opportunity (defense in depth)

`attestation.evidence.downstream_tls_binding{domain, spki_sha256}` gives an
attested SPKI pin. Wire it into the existing `UsesTLSBinding` machinery
(compare live upstream SPKI against the attested fingerprint,
constant-time) — this is strictly stronger than what venice has today and
mirrors the Tinfoil `TinfoilTLSKeyFP` flow.

### 5. Fixtures

Capture an ACI/1 model (`internal/capture`) and add
`internal/integration/testdata/venice_<aci-model>_<ts>/` alongside the two
existing dstack captures. Golden `report.txt` must show the enforced
factors' real status (Pass where verifiable, Fail where provenance is
absent) — fixtures must fail closed the same way live code does (AGENTS.md).

## Tests

- Parser unit tests from the captured ACI body: field mapping, strict
  unknown/missing detection, event-log replay, report-data binding.
- Format detection table: dstack body → `FormatDstack`; ACI body →
  `FormatACI`; `api_version: "aci/2"` → error; ambiguous body with both
  markers → deterministic result.
- Report-level test: ACI attestation with null provenance → the
  supply-chain factors Fail and `Blocked() == true` (regression that we
  never silently pass unverifiable models).
- Integration replay for one dstack and one ACI venice model; concurrent
  verification of both formats (the proxy serves both simultaneously —

## Constraints (AGENTS.md)

- Fail closed: unknown `api_version` or unparseable ACI structure is an
  error; unverifiable provenance is an enforced factor Fail, never
  `NotApplicable`.
- Strict parsing via `internal/jsonstrict`; unknown fields propagate to
  `response_schema`.
- Nonces originate from the client; confirm the ACI request carries our
  nonce and that `report_data` binds it (constant-time compare).
- Decompose the parser up front (structs + small mapping helpers) — gocyclo
  ≤ 32.

## Open questions

- What exactly does ACI/1 `report_data` bind (nonce? signing key? TLS SPKI?
  workload_id?) — must be reverse-confirmed from live responses before the
  `ReportDataVerifier` can be written. If the nonce is not client-bound,
  `nonce_match` must Fail for ACI models (and that blocks — correct).
- Is `workload_id` bound into the quote (MRCONFIGID or RTMR)? Determines
  the ACI analog of `compose_binding`.
- Does Venice plan to publish image digests / signed provenance for ACI
  workloads? Until then ACI models block on supply-chain factors by
  design — confirm maintainers want them listed (blocked) rather than
  delisted.
- `key_custody` and `workload_keyset` semantics — potential future factors,
  out of scope here.
