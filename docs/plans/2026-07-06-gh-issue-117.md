# Plan: GH issue #117 — response_schema factor chicken-egg problems

Issue: https://github.com/13rac1/teep/issues/117

## Context

`response_schema` (`FactorResponseSchema`, `internal/attestation/report.go:71`)
is a Tier 1/Core factor evaluated by `evalResponseSchema`
(`report.go:1128-1143`): Pass when `Raw.UnknownFields` and
`Raw.MissingFields` are both empty, Fail otherwise. Those fields come from
`jsonstrict.UnmarshalWarn` at each provider's parse step (Tinfoil:
`internal/provider/tinfoil/attestation.go:74,136-137`).

The chicken-egg: the Tinfoil V3 schema struct declares `NVSwitch
json.RawMessage \`json:"nvswitch"\`` (`attestation.go:31`) as a plain field,
so jsonstrict treats it as **required**. But `nvswitch` is legitimately
present only on ≥8-GPU Hopper machines — a fact we can only know from the
attested GPU topology, i.e. *after* authenticating the very response whose
schema we are checking. Today the same absent field simultaneously:

- **passes** `nvswitch_binding` — `evalNVSwitchBinding`
  (`report.go:1557-1583`) is topology-aware via `isNVSwitchExpected`
  (`internal/provider/tinfoil/verify.go:184-193`) and renders "NVSwitch not
  required for this GPU topology (verified absent)"; and
- **fails** `response_schema`, because `nvswitch` lands in `MissingFields`.

The current mitigation is blunt: `response_schema` sits in `DefaultAllowFail`
(`report.go:274`) *and every provider list* (:299, :317, :329, :354, :387,
:419, :431) — meaning schema drift never blocks anywhere, which also mutes
the genuinely useful unknown-field drift alarm.

## Design

Principle: **presence-of-conditional-fields is not a schema property; it is a
property of the authenticated attestation and belongs to the post-attestation
factor that consumes the field.** The schema factor should assert only what
is unconditionally true of the format. This removes the need for a global
deployment-topology map.

### 1. Make conditional fields structurally optional

- Change `v3Response.NVSwitch` (`tinfoil/attestation.go:31`) to an optional
  field in jsonstrict's model (pointer / optional annotation, per
  `internal/jsonstrict` semantics), so absence no longer produces a
  `MissingFields` entry. Enforcement of "nvswitch must be present when the
  topology requires it" already lives — correctly — in `nvswitch_binding`,
  which Fails when `NVSwitchExpected && !NVSwitchHashBound`
  (`report.go:1557-1583`). No security is lost: the conditional requirement
  is checked against authenticated data instead of unauthenticated wire
  shape.
- Audit the other provider schema structs for the same pattern (fields
  required by the struct but conditional in reality); each becomes optional
  in the struct + enforced by its consuming factor. `GPU`
  (`attestation.go:30`) stays required — it is unconditional per spec.

### 2. Split the factor's two meanings

`response_schema` currently conflates two different signals:

- **Unknown fields** — the provider sent data we don't model. This is a
  drift/tamper alarm and is cheap to keep strict. Per AGENTS.md, low-level
  parsers already return unknown fields to callers; the factor is the
  policy point.
- **Missing fields** — after change 1, a missing field means a genuinely
  unconditional field is absent, which will *also* fail the factor that
  needs it (signing key, quote, event log…), fail-closed where it matters.

Recommendation: keep one factor but rename the semantics in its detail
strings, and re-evaluate enforcement:

- Short term (this issue): after change 1 lands and fixtures confirm no
  false failures, remove `response_schema` from the per-provider allow-fail
  lists where it was added only for the nvswitch churn
  (`TinfoilCloudDefaultAllowFail` :419, `TinfoilDirectDefaultAllowFail`
  :431 — comments at :403-404, :424-425 say "while Tinfoil V3 attestation
  schema compatibility settles").
- Longer term (the broader re-categorization the issue alludes to): treat
  `response_schema` as the canonical example of a **format-conformance
  factor** distinct from **security factors**, and give the factor list an
  explicit category axis when that re-organization happens. Do not build the
  giant provider×model×machine schema map the issue warns about — change 1
  makes it unnecessary.

### 3. What NOT to do

- Do not filter `nvswitch` out of `MissingFields` inside `evalResponseSchema`
  based on topology — that makes the schema factor depend on the
  authenticated report it is notionally upstream of, recreating the
  chicken-egg inside one function and special-casing a provider in shared
  code.
- Do not have the parser drop or dedupe the field: AGENTS.md requires
  parsers to report unknown/missing fields to callers; optionality must be
  declared in the schema struct, not patched in the parser.

## Files

- `internal/provider/tinfoil/attestation.go` — `NVSwitch` optional; audit
  siblings.
- `internal/jsonstrict/` — only if the wrapper lacks an optional-field
  mechanism (pointer support); prefer using what `github.com/13rac1/jsonstrict`
  already provides.
- `internal/attestation/report.go` — detail-string clarity in
  `evalResponseSchema`; later removal of the factor from the two Tinfoil
  allow-fail lists.
- `internal/attestation/report_test.go`, tinfoil tests — coverage below.

## Tests

- Tinfoil V3 response **without** `nvswitch` (small-topology fixture):
  `response_schema` Pass, `nvswitch_binding` Pass ("verified absent").
- Tinfoil V3 response **with** ≥8-GPU Hopper topology but `nvswitch`
  **absent**: `nvswitch_binding` Fail (regression: the conditional
  requirement still bites, now in the right place).
- Response with a truly unknown field: `response_schema` Fail with the
  unknown-field detail (drift alarm intact).
- After the allow-fail removal: config tests asserting `response_schema` is
  enforced for tinfoil providers (mirror the existing
  `MergedAllowFail` test tables in `internal/config/config_test.go`).
- Replay fixtures in `internal/integration/` for both Tinfoil topologies.

## Verification

- `make check`; `go test -race ./internal/attestation/...
  ./internal/provider/tinfoil/... ./internal/jsonstrict/...`;
  `make integration` (both tinfoil fixture topologies must pass with
  `response_schema` enforced).

## Constraints (AGENTS.md)

- Fail closed: optionality is granted only to fields whose presence is
  conditional on authenticated attestation content *and* whose conditional
  requirement is enforced by a dedicated factor. Everything else stays
  required.
- Parsers keep returning unknown/missing fields to callers; policy stays in
  the evaluator.
- No special cases: no provider-specific branches inside
  `evalResponseSchema`.

## Open questions

- Does `internal/jsonstrict` (and the upstream `13rac1/jsonstrict`) already
  support optional fields via pointers? If not, that library change is the
  first (small) step.
- Inventory question: which other provider schema fields are conditional in
  reality? Run `make reports` across providers and diff
  `UnknownFields`/`MissingFields` occurrences to build the audit list before
  deciding each field's fate.
- The wider factor re-categorization (security vs. conformance vs.
  diagnostics axes) deserves its own issue; this plan deliberately fixes
  only the chicken-egg instance and the muted drift alarm.
