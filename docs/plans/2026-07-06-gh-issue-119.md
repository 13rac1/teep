# Plan: GH issue #119 — Dedicated tee_debug_disabled factor (and other hazardous TEE config bits)

Issue: https://github.com/13rac1/teep/issues/119

## Context — what already exists (important)

A `tee_debug_disabled` factor **already exists and is enforced everywhere**:

- `FactorTEEDebugDisabled = "tee_debug_disabled"`
  (`internal/attestation/report.go:66`), in `KnownFactors` (:438), absent
  from every allow-fail list → enforced by default for all providers.
  Gateway twin `FactorGWDebugDisabled` (:101).
- TDX: `tdxDebugBit = 0x01`, checked as `tdAttrs[0] & tdxDebugBit`
  (`internal/attestation/tdx.go:176-178`, :295-297) — TDATTRIBUTES bit 0
  (TUD.DEBUG), exactly the bit the issue asks about. So yes, TDX has the
  analogous flag and teep already checks it.
- SEV-SNP: `sevabi.ParseSnpPolicy(GuestPolicy)` → `policy.Debug` (bit 19)
  sets `DebugEnabled` (`internal/attestation/sev.go:190-196`); a redundant
  check in `validateSEVPolicy` (:208-234) also feeds
  `tee_hardware_config` via `PolicyErr`.

What the issue actually needs is therefore: (1) make the factor
**dedicated** (it is currently emitted inline from the parse-dependent
evaluators, coupled to quote parsing), (2) close the ground-truth gaps
(providers where the config bits aren't independently verified), and
(3) audit for **other** hazardous config bits beyond DEBUG.

## Design

### 1. Extract a dedicated evaluator

Today `FactorTEEDebugDisabled` is emitted inside `evalTDXParseDependent`
(`report.go:875-906`, emission :899-903) and `evalSEVParseDependent`
(:908-957, emission :948-954), plus the gateway variant in
`evalGatewayTDXParseDependent` (:2334-2369, :2361-2366).

- Add `evalTEEDebugDisabled(in *ReportInput)` registered in
  `buildEvaluators` (`report.go:778-831`) in Tier 1 order; remove the three
  inline emissions. Semantics per platform:
  - No parseable quote / parse error → **Fail** ("cannot determine debug
    state") — never Skip: an indeterminate debug bit on an enforced factor
    must block (the current parse-dependent structure gets this via
    Skip→Fail promotion; the dedicated evaluator should Fail directly with
    a clearer diagnostic).
  - `DebugEnabled == true` → Fail with the raw attribute/policy bytes in
    the detail (non-secret).
  - Otherwise Pass, detail naming the platform and the exact bit checked.
- Same extraction for the gateway factor.

### 2. Broaden to a hazardous-config-bits factor set

Audit and check the adjacent "single-bitflip compromise" bits. Data is
already parsed and available on `TDXVerifyResult` / `SEVVerifyResult`:

- **TDX** (`TDAttributes []byte` at `tdx.go:111`, `XFAM []byte` :114):
  beyond TUD.DEBUG (bit 0), evaluate SEPT_VE_DISABLE and the
  PKS/KL/PERFMON attribute bits, and XFAM feature mask sanity. Encode as an
  explicit allow-mask: known-good attribute bits pass, any *unknown/reserved
  set bit* fails (fail closed on novelty, mirroring the strict-config
  philosophy).
- **SEV-SNP** (`GuestPolicy uint64` at `sev.go:103`): beyond Debug (bit
  19), check MigrateMA (migration agent allowed), SMT policy, and
  SingleSocket per deployment expectations; go-sev-guest's `SnpPolicy`
  struct exposes them decoded. There is no "disable memory encryption" bit
  in SNP guest policy (encryption is structural), but PLATFORM_INFO's
  SMT/TSME bits in the report body are worth asserting — go-sev-guest
  exposes `PlatformInfo`.
- Implementation shape: either fold into the dedicated
  `tee_debug_disabled` (name kept, scope = debug only) plus a new
  `tee_policy_bits` factor for the rest, or one `tee_hazard_bits` factor.
  **Recommendation:** keep `tee_debug_disabled` narrowly scoped (its name
  is a public contract in `KnownFactors`/help) and add a new enforced
  factor `tee_policy_bits` for the remaining mask checks, following the
  new-factor checklist: constant (`report.go:61-108`), evaluator +
  registration, `KnownFactors` (:436-454), help entry
  (`cmd/teep/help.go`), NOT in any allow-fail list, not an `OnlineFactor`
  (offline-computable).

### 3. Ground-truth coverage per provider

The issue notes the bits are "not always fully enforced for all providers":

- Both verifiers run on the raw quote/report, so wherever teep sees a real
  quote (all current providers), the debug bit is independently verified —
  document this in `docs/attestation_gaps/`. The NearAI gap
  (`docs/attestation_gaps/dstack_integrity.md`) concerns *measurement
  golden values*, not the debug bit; the debug bit needs no provider
  ground truth because it is read from the signed quote body itself.
- The real dependency is H1: the bit is only as trustworthy as the quote
  signature. Note in the factor docs that `tee_debug_disabled` presumes
  `tee_quote_signature`/`tee_cert_chain` enforcement (fable-review H1 plan,
  `docs/code-review/2026-07-02-h1-fix-plan.md`) — a provider whose quote
  signature is allow-failed can forge the debug bit too. This is the
  "regardless of other integrity checks" caveat in the issue, inverted:
  the dedicated factor is necessary but sufficient only with H1 fixed.
- Tinfoil: TDX attribute policy currently flows through
  `TinfoilSC.TDXPolicyDetail` (`report.go:1038-1045`) — after this change
  the debug/policy bits are checked by teep directly from the quote, so we
  no longer "accept whatever they tell us" for these bits.

## Tests

- Table-driven evaluator tests: debug bit set (TDX bit 0 / SNP bit 19) →
  Fail + `Blocked() == true` for every provider default allow-fail list
  (regression: no list may ever exempt it — add an explicit test asserting
  `tee_debug_disabled` and `tee_policy_bits` are absent from all
  `*DefaultAllowFail` slices).
- Indeterminate case: nil TDX+SEV results → Fail (not Skip), blocked.
- Unknown/reserved TDX attribute bit set → `tee_policy_bits` Fail.
- SEV MigrateMA set → Fail.
- Regenerate golden `report.txt` fixtures (they still show stale `tdx_*`
  factor names vs. current `tee_*` constants — clean that up in the same
  pass).

## Verification

- `make check`; `go test -race ./internal/attestation/...`;
  `make integration` (all provider fixtures must still pass — genuine
  production quotes have debug clear, so no false positives expected);
  `make reports`.

## Constraints (AGENTS.md)

- Fail closed: indeterminate debug state fails; unknown set bits fail.
- New factors enforced by default via the inverted model — do not add them
  to any allow-fail list, and add the test that pins that.
- No provider special cases in the evaluator; platform (TDX/SEV) switching
  only.

## Open questions

- Exact allow-mask for TDX TDATTRIBUTES/XFAM: derive from current captured
  quotes across providers (`make reports`), then lock. Any bit not observed
  and not documented as safe starts out forbidden.
- Should SEV SMT/SingleSocket be enforced globally or per-provider
  expectation? (SMT-on is common in production; blocking on it globally
  would fail most providers — candidate for measurement-policy-style
  configuration rather than a hard factor.)
- Whether to fold `validateSEVPolicy`'s debug duplication out of
  `tee_hardware_config` once the dedicated factor exists (avoid
  double-reporting the same bit under two factors).

## Addendum — `tee_policy_bits` implementation (deferred part, closed out)

Implemented as `FactorTEEPolicyBits = "tee_policy_bits"`
(`internal/attestation/report.go`), `evalTEEPolicyBits` registered in Tier 1,
enforced by default (absent from every `*DefaultAllowFail` list — see
`TestTEEPolicyBitsNeverAllowFailed`). It is core-only; there is no
`gateway_tee_policy_bits` twin (the gateway is TDX-only and the TDX branch
below is deliberately not fail-closed on novel bits yet, so a gateway twin
would add no enforcement value today).

**SEV-SNP branch** (`sevPolicyBitsFactor`): fails closed. Guest-policy bits
are a small, ABI-defined surface, so:
- MIGRATE_MA (bit 18) is explicitly forbidden (migration-agent memory/key
  access is a real hazard).
- Any bit outside `sevPolicyKnownGoodMask` — ABI-version bits 0-15, SMT (16),
  reserved-must-be-1 (17), SINGLE_SOCKET (20), CXL_ALLOW (21),
  MEM_AES_256_XTS (22), RAPL_DIS (23), CIPHERTEXT_HIDING (24) — is forbidden.
  This also catches DEBUG (bit 19) and any bit ≥ 25 (undefined in the
  current ABI).
- Verified against the real captured Tinfoil SEV value `guest_policy =
  0x30000` (bits 16+17): passes.

**TDX branch** (`tdxPolicyBitsFactor`): intentionally **not** fail-closed on
novel TD_ATTRIBUTES/XFAM bits. Running the full integration fixture suite
with the debug logging added in `04b38b0` showed every current provider
(venice, venice ACI, nearcloud + gateway, neardirect, chutes, tinfoil
direct/cloud) presents the identical TD_ATTRIBUTES shape: only bit 0
(TUD.DEBUG, already covered by `tee_debug_disabled`) and bit 28
(SEPT_VE_DISABLE) vary from zero, and bit 28 is always set. That is a
single-shape sample across today's fleet, not evidence about the full space
of legitimate TD_ATTRIBUTES/XFAM configurations other operators might use —
fail-closing on "any other bit" here risks blocking a legitimate provider
the first time hardware/firmware or a dstack version changes XFAM (a
feature mask that varies by CPU generation) or sets an attribute bit we
haven't seen (e.g. PKS/KL/PERFMON). Per the overriding constraint (a wrong
mask here is a fail-CLOSED regression that takes providers offline), the
TDX branch instead **Passes** with `TD_ATTRIBUTES`/`XFAM` raw hex and the
decoded `sept_ve_disable` flag in the detail string, so drift is visible in
every verification report (in addition to the existing debug-level slog
logging) without blocking. Confirmed `TD_ATTRIBUTES = 0x0000000010000000`
(SEPT_VE_DISABLE set) passes, matching the real Tinfoil TDX capture.

**Follow-up (still open, tracked here and not newly implemented):**
per-provider TOFU pinning of the TDX *variable* config bits (TD_ATTRIBUTES
bits beyond the hazard bits handled above, XFAM, and SEV `platform_info`)
once enough real captures exist across providers/hardware generations to
define a safe per-provider allowlist without risking false-closes. The
values are logged (`04b38b0`) so operators can already detect drift
manually in the interim.
