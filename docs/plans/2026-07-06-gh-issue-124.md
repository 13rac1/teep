# Plan: GH issue #124 — Reasoning loss due to provider and model name heuristics

Issue: https://github.com/13rac1/teep/issues/124

## Context

Agent frameworks (LiteLLM, code agents, ReAct loops) decide how to preserve
reasoning content between tool calls and across turns using heuristics keyed on
provider/base-url and model name. Teep's client-facing model IDs are
`provider:model` (`prefixModelID`, `internal/proxy/proxy.go:3377`) and its base
URL is a localhost proxy, so those heuristics never match. Result: frameworks
drop reasoning entirely, append "prompt reminder" user messages that cause
model chat templates to strip same-turn reasoning ("prompt sandwiching"), and
omit model-specific cross-turn preservation flags.

PR #123 (merged, `internal/proxy/reasoning.go`) added detection and partial
repair for `/v1/chat/completions` only:

- **Case 1** (reasoning dropped by framework): detected via
  `chatRequestStatsFromRaw` (`reasoning.go:103`); prior-turn omissions log INFO,
  ≥2 active-turn omissions log WARN (`activeMissingReasoningWarnThreshold`,
  `reasoning.go:17`). Detection only — teep cannot restore content the
  framework never sent.
- **Case 2** (trailing user message after tool output strips same-turn
  reasoning): detected by `annotateTrailingUserReasoningLoss`
  (`reasoning.go:349`).
- **Case 3** (missing chat-template preservation flag): detected and
  **repaired** by `repairChatReasoningPreservationWithStats`
  (`reasoning.go:920`) → `injectChatTemplateBool` (`reasoning.go:977`), for
  three hardcoded families (`reasoning.go:868`): `glm` →
  `clear_thinking=false`, `kimi` → `preserve_thinking=true`, `deepseek` →
  `drop_thinking=false`.

The repair hooks into `handleEndpoint` after `rewriteModelInBody` and before
relay/encryption (`proxy.go:1550-1559`), so injected flags reach the upstream
(including E2EE-wrapped bodies). Diagnostics are rate-limited to 1/hour per
category (`hourlyLogLimiter`, `reasoning.go:703`) and never log message text.

## Remaining gaps (why the issue stays open)

1. `/v1/responses` is registered (`proxy.go:544`, served for
   `tinfoil_v3_cloud`/`tinfoil_v3_direct` via `ResponsesPath`, `proxy.go:824`,
   `:848`) but the diagnostics/repair are gated on `EndpointChat` — the
   Responses API path has zero reasoning-loss visibility.
2. The family→flag map covers GLM/Kimi/DeepSeek only. Qwen, NemoTron Ultra,
   and MiniMax M2.7 are known-affected (issue body) with no coverage.
3. The root cause — frameworks not recognizing teep model names/base-url — is
   untreated. `provider:model` IDs defeat substring heuristics that would
   otherwise match (`deepseek`, `glm`, etc. survive as substrings, but
   heuristics that anchor on prefix, exact id, or provider name do not).
4. Case 2 is detect-only. For models whose templates have no preservation
   flag, the prompt-sandwich strip has no server-side mitigation.
5. No empirical verification that preservation actually works end-to-end.

## Proposed changes

### Phase 1 — Extend diagnostics/repair to `/v1/responses`

- Add a Responses-API stats parser alongside `chatRequestStatsFromRaw`. The
  Responses body shape differs: `input` is an item array with typed entries
  (`message`, `function_call`, `function_call_output`, `reasoning`), plus
  `previous_response_id` server-side state. Detection maps:
  - Case 1 analog: assistant turns in `input` with `function_call` items but
    no adjacent `reasoning` item.
  - Case 2 analog: trailing `message`(user) item appended after
    `function_call_output` items.
  - Additional Responses-specific signals: absence of
    `include: ["reasoning.encrypted_content"]`, `store:false` combined with no
    reasoning items replayed, and `reasoning.effort` present but no reasoning
    items round-tripped.
- Gate on `ep.endpointType == e2ee.EndpointResponses` in `handleEndpoint`;
  reuse `hourlyLogLimiter` with new log keys, and the same
  `reasoning_diagnostics_issue` attribute.
- Repair: whether `chat_template_kwargs` injection is meaningful on
  `/v1/responses` depends on the upstream (Tinfoil) accepting it. First step is
  detection + WARN only; add injection once confirmed against a live Tinfoil
  endpoint (gate the confirmation test behind `TEEP_LIVE_TESTS`).

### Phase 2 — Broaden the model-family flag map

- Add entries to `modelReasoningPreservationCheck` (`reasoning.go:868`) for
  families with documented template flags; confirm each against the model's
  published chat template before adding (do not guess — a wrong kwarg is
  silently ignored by some servers and rejected by others):
  - `qwen` (Qwen3 templates: no cross-turn flag; same-turn preservation is
    template-automatic when reasoning is delivered — so Qwen is Case 2
    detection-only, document that).
  - `minimax` (M2.7 template flag, if published).
  - `nemotron` (Ultra template flag, if published).
- Keep the map data-driven: extract the family table into a package-level
  immutable slice of structs (name, kwarg, value, repair reasons) so adding a
  family is a one-line change with table-driven tests. This stays within the
  AGENTS.md rule (immutable package-level data is allowed; no post-init
  writes).

### Phase 3 — Model-name normalization for framework heuristics (root cause)

Two complementary options; both preserve AGENTS.md "routing MUST ensure
uniqueness and determinism":

- **Option A (recommended): configurable model aliases.** New per-provider
  config table `model_aliases` mapping client-facing alias → upstream model.
  `handleModels` advertises the alias verbatim (no `provider:` prefix);
  `resolveModel` (`proxy.go:912`) checks the alias table before the
  `provider:model` split. Startup validation rejects: duplicate aliases across
  providers, aliases containing `:`, and aliases colliding with an existing
  `provider:` prefix — fail closed at config load per AGENTS.md. This lets an
  operator expose `deepseek-ai/DeepSeek-V3.2-Exp` exactly as LiteLLM expects.
- **Option B: separator normalization.** Advertise `provider/model` (slash)
  instead of `provider:model` where frameworks treat the segment after the
  last `/` as the model name. This is a breaking client-facing change; if
  pursued, it must be a hard cutover (no dual-accept fallback — AGENTS.md "no
  backwards compatibility"), which argues for Option A instead.

Alias resolution must be covered by concurrent tests (multiple goroutines
resolving aliases + prefixed names) since it sits on the hot request path.

### Phase 4 — Opt-in prompt-sandwich merge repair (Case 2 mitigation)

For models with no template flag, the only server-side fix is to merge the
appended trailing user "reminder" message into the previous real user message
so the template does not see a new user turn:

- Strictly **opt-in** per provider or globally (`repair_prompt_sandwich =
  true`); default off, because it mutates client request semantics.
- Implementation: when `annotateTrailingUserReasoningLoss` fires and the
  model family has no preservation flag, concatenate the trailing user
  message content onto the prior user message (with a `\n\n` join), preserving
  all other fields; WARN (rate-limited) that the repair was applied.
- Never applied to E2EE-encrypted-field providers where message content is
  ciphertext at this layer — detect and skip with a WARN explaining why.
- If the merge cannot be performed losslessly (non-string content parts,
  attachments), do nothing and WARN — no partial rewrites (fail loudly, not
  half-open).

### Phase 5 — Empirical verification harness

- Add a live integration test (gated behind `TEEP_LIVE_TESTS`) implementing
  the marker-counting self-detection prompt from the issue comment
  (GLM-5.2 `=== THINKING STEP N ===` protocol): drive a short tool-call loop
  through teep and assert the model reports N > 1. This is the only way to
  prove end-to-end preservation rather than inferring it from request shape.
- Unit tests: extend `reasoning_internal_test.go` tables for each new family,
  the Responses parser, alias resolution, and the merge repair (including the
  must-not-merge cases).

  at least one GLM and one DeepSeek provider model.

## Constraints (AGENTS.md)

- Never log message content — detection stays metadata-only (roles, counts,
  field presence). L4-style prefixes are not acceptable here.
- Alias config validation fails closed at startup on any ambiguity.
- No fallbacks: Option B dual-accept is ruled out; merge repair is opt-in and
  all-or-nothing per request.
- Concurrency: alias table is read-only after config load; repair path
  allocates per-request (no shared mutable state) — keep it that way.

## Open questions

- Does the Tinfoil `/v1/responses` upstream accept `chat_template_kwargs` (or
  an equivalent) at all? Determines whether Phase 1 gets a repair step.
- Which exact template flags exist for MiniMax M2.7 and NemoTron Ultra?
  (Confirm from upstream chat templates before adding families.)
- Should aliases be auto-generated (strip prefix when unambiguous across
  providers) in addition to explicit config? Auto-generation risks collision
  churn when providers add models; explicit-only is safer and is the
  recommendation here.
